## 1. 背景与问题

### 1.1 用户问题

长会话（几十分钟到数小时、多任务多代理）里，用户会遇到：

1. **执行前看不见计划**：任务清单只在 AI 脑子里或散在对话里；
2. **执行中不知道进度**：翻聊天记录才能判断做到哪；
3. **完成后无法复盘**：不知道每个任务花了多久、任务之间等了多久、时间花在哪儿；
4. **计划会变但看不到变化**：中途插入任务、拆分支线后，没有「计划 vs 实际」的对照；
5. **多会话任务互相孤立**：A 会话的任务在 B 会话不可见，也分不清哪个会话在做什么。

### 1.2 DSH 现有能力与缺口

| 现有 | 缺口（本产品价值） |
|---|---|
| 官方 Trajectory：按轮次的事件记录表 + 交互式耗时概览 | 只有事件/消息级；没有任务级图、依赖、回放、等待拆解 |
| 官方 Agent Teams 任务板：只读 roster + 任务列表 | 没有图/甘特/回放；不显示耗时与等待；无跨会话目录 |
| `todo_write` 清单 | 只显示最新清单，无历史回放与耗时 |
| jobs/subagent/usage 分散展示 | 没有汇合到任务视角 |
| **等待时间** | **全生态当噪声折叠；本产品把等待作为一等指标** |

### 1.3 已验证的可行性

- 会话日志包含 41 类事件，全部带 `seq` + 毫秒时间戳；`team/task` 直接带 `blockedBy`、`ownerId`、`writeScopes`；
- M0 已在隔离真实实例验证：session 投影、Agent 工具、插件 HTTP 路由、三个 UI slot、会话页签、`useProjection('taskMap')` 均可用（见 [M0-SPIKE.md](../M0-SPIKE.md)）；
- 用真实会话做了交互原型（任务图/甘特/回放/等待拆解），视觉与数据推导成立。

## 2. 产品定位

### 2.1 一句话

**DSH 里最好用的「会话任务复盘与等待分析」插件**：不只告诉你「做了什么」，还告诉你「等了多久、卡在哪里」。

### 2.2 目标用户

| Persona | 场景 | 关键诉求 |
|---|---|---|
| 个人开发者 | 让 AI 做多步开发/调研，一跑半小时 | 中途看进度；结束后复盘时间去向；找出等待/卡点 |
| Team Lead（Agent Teams） | 8 个任务分给 5 个 teammate | 图上看依赖与支线；哪个代理在等；插入/拆分后计划怎么变 |
| 复盘/汇报者 | 把一次会话成果讲给别人 | 截图/导出；关键节点与耗时一目了然 |

### 2.3 非目标（明确不做）

- ❌ 不创建/修改/调度任务（调度权归 AI / Agent Teams）；
- ❌ 不写会话日志、不改历史事件；
- ❌ 不合并不同会话的任务（避免 task id/负责人混淆）；
- ❌ 不做通用流程挖掘/跨产品 trace 平台；
- ❌ MVP 不做云端协作、分享链接、LLM 自动撰写复盘（P2+）。

## 3. 场景与用户故事

> 每条都是可验收的 Given/When/Then。MVP 必须覆盖 US-1~US-7；P1 覆盖 US-8；P2 覆盖 US-9。

| ID | 用户故事 | 验收要点 |
|---|---|---|
| **US-1** | 作为用户，AI 开始多步任务前，我想看到它规划的任务清单 | 会话内页签打开可见：任务数、每任务标题/负责人/依赖/状态；空板时明确提示「本会话未维护任务清单」 |
| **US-2** | 作为用户，执行中我想看到走到哪一步 | 任务状态实时变化（待开始/执行中/完成/失败）；进行中任务显示「已跑」计时；无需刷新 |
| **US-3** | 作为用户，结束后我想复盘整个执行过程 | 回放支持播放/暂停/倍速/拖动；任意时刻能还原节点状态、时间轴与统计；未发生的未来不剧透 |
| **US-4** | 作为用户，我想知道每个任务花了多久、任务间等了多久 | 详情显示：执行耗时、排队等待、依赖阻塞、总周期；总览显示等待拆解（会话前空闲/任务排队/依赖/等待代理/审批） |
| **US-5** | 作为用户，我点击任务想知道它具体干了什么 | 详情显示状态区间、依赖、写入范围、时间窗内工具/job 过程、跳转到开始/完成 |
| **US-6** | 作为用户，AI 执行中我让它「插一个任务」，我希望面板体现出来 | 新任务节点出现；`NEW` 标记；计划基线 diff 显示「新增 1」；回放中在插入时刻出现 |
| **US-7** | 作为用户，我让 AI「把任务拆成两条支线」，我希望图上有分叉 | 父子关系记录并渲染；变更记录「14:32 拆分 task-4 → task-9/10」；父任务状态不被插件改写 |
| **US-8** | 作为用户，我开了很多会话，想在一个地方看到哪些会话有任务、进展如何 | 全局页按工作区分组：标题/时间/任务统计/状态；点击进入单会话；**不合并任务** |
| **US-9**（P2） | 作为用户，我在 B 会话问「A 的任务做到哪了」，AI 能回答 | AI 调 `task_map_query` 只读返回 A 的任务摘要；只返回权限内会话；不泄露完整内容 |

**关键示例对话**（产品验收时直接照着说）：

- 「在 T4 后面插一个任务：补充飞书扫码登录测试」→ 8→9；
- 「把 T4 拆成 T4a 数据导入、T4b 员工导入 UI 两条支线」→ 父任务下两个子节点；
- 「这次会话时间都花在哪？哪个任务等最久？」→ 回答引用面板的等待拆解。

## 5. 交互与视觉规范

### 5.1 信息架构与入口

```text
单会话（MVP）：会话页签「任务地图」——只显示本会话任务
跨会话（P1）：顶栏「☰ 全部会话」/ 左侧栏整页——按工作区分组，只列有任务板的会话，点击进入
常驻摘要（P1）：输入框上方小条——当前任务 + 已跑 + 等待
AI 查询（P2）：B 会话对话 → AI 调 task_map_query
```

### 5.2 布局（与原型一致）

- 顶栏：会话标题/统计、回放控制、全局入口；
- 左上：任务流程图（S 形 + 依赖 + 轨迹）；
- 左下：甘特时间轴（任务/代理/事件/热度），可拖播放头；
- 右侧：总览/任务详情；
- 空状态：无任务板 → 说明 + 「如何让 AI 维护任务」提示；
- 错误状态：投影不可用/数据不完整 → 局部提示，不崩页。

### 5.3 回放规范

- 时钟：单一 `currentTime` store，`requestAnimationFrame` 推进；
- 速度：60×/120×/300×/600×；
- 未来不剧透：时间之后的状态置灰/隐藏；
- 未完成任务：显示「已跑 X」（前端 tick，不写投影）；
- 拖拽：任务条点击选中；空白拖动 scrub；键盘可操作；
- 回放结束：保留结束态，可一键重播。

### 5.4 视觉

- 主题：跟随 DSH，使用 `--dsw-alias-*` 变量；插件类名统一前缀 `tm-`；
- 状态色：待开始灰、执行中琥珀、完成绿、失败红；负责人色条来自稳定调色板；
- 字体/密度：与 DSH 一致，节点文字可截断 + tooltip；
- 不引入外部 UI 库；SVG 手绘（原型已验证）。

### 5.5 文案

- 中文优先；英文可后补；
- 面向客户不出现内部实现词（job/worker/MCP/prompt 等），用「后台任务/执行过程」；
- 推断数据必须标注（「按时间窗推断」）。

## 6. 数据与指标

### 6.1 数据来源（全部来自会话事件，不埋点）

| 数据 | 事件 | 说明 |
|---|---|---|
| 任务 | `team/task`（全量快照，含 `blockedBy/ownerId/writeScopes/status/revision`） | 首选 |
| 单 agent 任务清单 | `todo/write`（全量列表） | 无 team 时降级 |
| 成员/支线 | `team/member`、`subagent/descriptor`、`subagent/catalog` | 负责人、子会话 |
| 时间骨架 | `turn/start` / `turn/end`、`step/start` / `step/end` | 人工空闲、step 耗时 |
| 工具/后台 | `tool/call` / `tool/result`、`job/registered` / `job/settled` | 过程与耗时 |
| 等待 | `approval/asked` / `approval/decided`、`wait_agent` 工具调用 | 审批/代理等待 |
| 成本 | `assistant/message.data.usage` | token |
| 关系 | 插件工具 `task_map_record_relation` 的 `tool/call` 参数 | 只记录展示关系 |

### 6.2 指标口径

| 指标 | 公式 |
|---|---|
| 任务执行耗时 | `completedAt − startedAt`；进行中显示 `now − startedAt` |
| 排队等待 | `startedAt − createdAt` |
| 依赖阻塞等待 | `max(blockedBy.completedAt) − createdAt` |
| 就绪后延迟 | `startedAt − max(blockedBy.completedAt)` |
| 任务交接间隔 | `next.startedAt − prev.completedAt` |
| 代理等待 | Σ `wait_agent` span（与回放区间相交） |
| 审批等待 | `approval/decided − approval/asked` |
| 人工空闲 | `next turn.start − turn.end`（含会话创建→首轮） |
| 执行累计 | Σ 任务执行耗时（并行时 > 墙钟，UI 标注） |
| Token | Σ `usage`（输入/输出/缓存读） |

### 6.3 归属规则

- **负责人精确**：`team/task.task.ownerId` → `team/member.id`；等于 Lead session id 表示 Lead 亲自执行；
- **执行过程推断**：事件无 `taskId` 外键；MVP 按任务 `in_progress` 时间窗与 tool/job 重叠推断，UI 标注「推断」，并行任务可重复归因；
- P1 可在工具调用参数中约定 `task_id` 提升归属精度（不强制）。

### 6.4 数据完整度与降级

```text
team/task（团队模式）
   ↓ 无
todo/write（单 agent 计划模式）
   ↓ 无
不显示伪造任务：提示「本会话未维护任务清单」，只展示事件级信息（P1 可补推算 episode）
```

## 7. 技术方案摘要

> 完整技术细节见 [技术方案](../../dsh-task-map-research/docs/02-技术方案与开发计划.md)；M0 已验证的结论见 [M0-SPIKE.md](../M0-SPIKE.md)。

### 7.1 架构

```text
Host（index.js）
  · ctx.on('session/event') 可选实时旁路
  · sessionProjections.register('taskMap') → fold 事件 → wire.view 下发
  · tools.register: task_map_ping / task_map_record_relation（P2: task_map_query）
  · webServer.register: /task-map/api/*（历史/详情/导出；P1 会话目录）
Client（client.js，CJS factory + 平台 React）
  · conversation.view「任务地图」（MVP）
  · main + sidebar.panellist（P1 全局页）
  · conversation.composer.dock（P1 小条）
  · SVG 手绘任务图/甘特/回放；单一 clock store
```

### 7.2 M0 已验证（直接复用，不要重做）

- `conversation.view` 只注册 slot 就能出现页签（无需 ViewMap 注册）；
- `useProjection('taskMap')` 可读到第三方投影值（`asOfSeq` 非空）；
- host 投影/工具/路由注册；client bundle 进入 boot graph；sidebar/main 正常；
- 本地 host/client smoke 测试范式。

### 7.3 必须修的问题

- ⚠️ **插件自注册 HTTP 路由不过 DSH 鉴权**（M0 实测无 token 也 200）：MVP 必须加 `Origin` / `Sec-Fetch-Site` 校验，移除调试字段；
- hero（未选中会话）页曾出现一次 `session-maybe` slot 装配告警：M1 用禁用插件 A/B 定位；若是本插件造成，改为会话存在后再注册/渲染；
- 投影 `apply` 同步、无关事件返回同一引用；`wire.view` 结果大小 ≤200KB；
- `ctx.effect` 清理所有注册；错误不得冒泡到宿主。

### 7.4 目录与构建

```text
dsh-task-map/
├─ package.json / cordis.patch.yml / locale/ / icon（可选）
├─ index.js            # Host
├─ client.js           # Client（单文件 CJS；MVP 不引入构建链）
├─ test/               # host-smoke / client-smoke / fold / e2e
├─ docs/               # 本方案、M0 报告、截图
```

## 12. 执行规范（新会话必读）

### 12.1 开工动作（按顺序）

1. 读 [`../../tmp/handoff/20261105-031500-dsh-task-map-dev.md`](../../tmp/handoff/20261105-031500-dsh-task-map-dev.md)（交接文件）；
2. 读本方案 §0/§8/§9，确认 M1 起点；
3. 在本会话创建任务板（用 team_task_*），至少按 M1 的 W1.1~W1.6 建任务 + 依赖；
4. 先跑 `node test/host-smoke.mjs` 与 `node test/client-smoke.mjs` 确认基线绿；
5. 开始 W1.1。

### 12.2 工作方式

- **单写者**：同一时刻只改 `dsh-task-map` 内的文件；若用多 agent，写范围按目录/文件拆分并在任务板标注；
- **先数据后 UI**：M1 未通过不开始 M2；
- **每完成一个工作包**：跑测试 → 更新任务板 → 在 `docs/进度日志.md` 记一行（日期/包/结果/下一步）；
- **不碰用户环境**：安装/启动一律用隔离 `DSH_HOME=~/.dsh-lab`；禁止改 `~/.dsh` 或桌面 profile；需要真实验证时先建隔离 home 的副本；
- **不编数据**：文档/测试/截图必须来自真实事件或真实实例；
- **不确定就问**：产品口径变更（尤其是「关系是否参与调度」「是否合并跨会话任务」）必须先问用户。

### 12.3 提交/版本

- 建议在 `dsh-task-map/` 初始化 git（`git init` + `.gitignore` 排除 `.dsh-lab`、`node_modules`）；
- 每个里程碑一次 commit；commit message：`feat(m1): fold team/task events and golden tests`；
- 不在仓库中存放真实凭据/完整原始会话（fixture 脱敏裁剪）。

### 12.4 完成定义（对用户汇报）

- 报告结构：做了什么 → 证据（测试/截图/黄金值）→ 未做/风险 → 下一步；
- 必须给出可复现命令；
